# How cis_database works

What a call waits for, how writes reach MariaDB, how the boot copy works, and which reads MariaDB answers.

## What a query waits for

A successful `INSERT`, `UPDATE`, `DELETE` or transaction returns when SQLite has the change on disk: the write commits at once, and its caller is answered after an `fdatasync` of the WAL that covers it has finished, so an answered write survives a power cut or an OS crash as well as a crash of the server. The sync runs on libuv's thread pool, never on the server thread, and one sync answers every write waiting for it. A sync that fails answers nothing: its writes wait, their rows stay out of MariaDB, and the sync is retried after 1 s, doubling to 30 s, until one succeeds. The console and `cis_database_doctor` report the failures. The WAL file is grown with zeros at boot to the size it reaches before SQLite starts it over, so a commit only overwrites blocks the file already has and its sync is a plain data flush with no filesystem journal commit (0.21 ms median on an SSD VPS, against 0.75 ms for a sync after the file grew; benchmark VPS run, 2026-11-01, local). This is what MariaDB does with `innodb_flush_log_at_trx_commit=1`. Reads are answered at once. `set cis_database_ack "process"` answers writes at commit instead (safe from a crash of the server, not from a power cut). A write does not wait for MariaDB: the copy to MariaDB runs in the background, about every 50 ms, and only sends rows a finished sync covers, so after a power cut MariaDB never holds a write SQLite lost.

Every write MariaDB has not confirmed is a row in an outbox table inside the same SQLite file, committed in the same transaction as the write itself. A crash, a `kill -9` or a stop with MariaDB down loses nothing: the outbox is sent after the next start, in the original order, a transaction as a whole. The copy marks the last row it applied inside the same MariaDB transaction, so a crash in the middle of a copy never applies a write twice. Nothing waits in memory, and there is no size limit beyond disk space. The outbox and its state tables start with `__cis_`; callers cannot read or write them.

The resource never holds the server thread for long. Its work in one stretch (SQL, its own JavaScript, and the Lua callbacks it resumes) is measured; past `cis_database_slice_ms` (4 ms) the rest waits for the next turn of the event loop, in arrival order: results are handed back a moment later and new calls queue behind earlier ones. A burst of thousands of calls from one tick, or a script awaiting a long loop of queries, is spread over many short slices instead of freezing the tick. One statement is never split, so a single slow query still takes as long as it takes. A statement, a transaction, an `execMany` list or a checkpoint copy that holds the server thread for 50 ms or more prints one console line with its caller and its SQL, every quoted string and number shown as `?` (at most one line of each kind every 10 s, with a count of the ones left out), so a hitch points at the SQL behind it. The next slice is woken by a one-byte datagram the resource sends itself on 127.0.0.1, read on the event loop's next turn in about 0.2 ms inside FXServer; timers there fire once per server frame (about 50 ms) and file-system callbacks queue in libuv's thread pool. There is also a budget per server frame: once 25 ms of this work has run since the last server tick, everything else waits for the next tick, so several slices cannot add up to a hitch. That leaves half of the 50 ms tick to entity sync, routing and the other resources. Set `frameBudgetMs` in `config.json` (or the convar `cis_database_frame_ms`) to change it: a lean server on fast hardware can raise it for more throughput, and 0 turns it off. The copy to MariaDB counts against both budgets and is sent in batches of about 1 MB of SQL.

A SELECT that reads a whole table holds the server thread for the whole scan (MariaDB is as slow, but runs elsewhere). When the same single-table SELECT has taken 3 ms or more three times and SQLite's plan scans the table, SQLite gets an index on its equality columns, then its ORDER BY column when there is a LIMIT, and the console says which. These indexes exist in SQLite only: they are never sent to MariaDB, `SHOW INDEX` and `information_schema` do not list them, and `ALTER TABLE` drops a table's own before it runs. At most 4 per table and 32 in all; on a table over 100000 rows the console names the index to add instead of building it. An index changes how fast a query runs, not what it returns, except that rows tied on ORDER BY may come back in another order, as MariaDB does not promise one either.

SQLite syncs to disk only at a checkpoint, which copies the WAL into the database file. The two syncs of a checkpoint (the WAL, then the database file) run on libuv's thread pool in the order SQLite uses; only the copy runs on the server thread, once every 256 writes. SQLite copies every frame written since the last pass in one call and cannot copy part of them, so a pass after a burst of large writes takes longer: in every cis_bench run on the benchmark VPS (635 phase reports; benchmark VPS run, 2026-11-01, local) the longest copy took 22.6 ms, during the schema phase (14.4 ms during the seed import), and in the phases with players (live, save, payday, saturation) it stayed under 8 ms.

While the server runs, the SQLite file in `cache/` answers the game and MariaDB is the copy. On boot the resource compares each table with MariaDB and copies again every table MariaDB changed, so edits made in MariaDB while the server was stopped are what the game reads. The comparison is MariaDB's `CHECKSUM TABLE` against the sum recorded when SQLite last copied that table, plus the table's columns and indexes; a table where both still match is not copied. A table the game wrote during the last session has a new sum, so it is copied again at the next start. A table with writes still in the outbox (a crash, or a stop with MariaDB down) is the exception: it keeps its SQLite copy, so a write that had not reached MariaDB before the crash is still there after the restart. Those writes are sent to MariaDB once it answers, and the table is then copied once more. A table is copied in small steps (deletes of 1,000 rows, inserts in transactions of 100 rows) with the server thread handed back between them. On a local test with 114 tables and 92,000 rows, a first start copies everything in about 2 s and a start with nothing changed takes about 0.3 s; no step held the thread for 100 ms or more (`tests/repro/maria_boot_copy.js`). On the benchmark VPS (a qbox server, 115 tables, 92,196 rows, build `ae3a7a5`; benchmark VPS run, 2026-11-01, local), a first start copied everything in 11.8 s, a restart with nothing changed was ready in about 4 s, and no tick of this resource took more than 42 ms during either. Nothing answers until the copy is done, so start the server before players join.

The one exception is a SQLite file older than MariaDB: `cache/` restored from a backup, a resource folder copied with its `cache/` to another server on the same MariaDB, or a file that lost its last writes in a power loss after MariaDB had them. MariaDB records how far it has copied each file (`__cis_replica_state`), and a file whose writes stop below that mark is older. The console then says so, the writes made since the file was opened are sent under a new mark, and every table without writes still waiting for MariaDB is copied again from MariaDB before the server answers calls (at the next start, when MariaDB did not answer at this one). To start a server from MariaDB alone, stop it and delete `cache/` instead of restoring an old one.

A call that arrives before that copy has finished waits: queries, inserts, updates, transactions, `execMany`, and the `_async`/`Sync` forms alike. Waiting calls run in the order they arrived as soon as the copy is done. The game thread is not blocked while they wait. If the resource stops first, they fail with `engine not ready`. The internal `hydrate` export, which copies tables again while the server runs, holds every call the same way until it ends, and `isReady` stays true. Nothing in the resource calls it and other resources are refused, so it never runs on its own. A full copy holds calls for as long as the boot copy takes (seconds for 90,000 rows from a remote MariaDB), so run it only with no players on.

On a first install, if MariaDB does not answer, the resource retries and `isReady` stays false. It does not hand other resources an empty database. When the SQLite file already has the game's tables, the resource starts from it without MariaDB and keeps writes in the outbox until MariaDB answers.

A write SQLite refuses fails for the caller. It is never run on MariaDB instead, which would leave the two databases apart. A read SQLite cannot run may still be answered by MariaDB.

## Reads MariaDB answers

With MariaDB configured, a read goes to SQLite only when SQLite is known to answer it exactly as MariaDB and oxmysql would. Every other read is answered by MariaDB, so a caller never gets a value that differs from oxmysql's without being told. SQLite answers a `SELECT` whose result columns are plain columns or `COUNT`, and whose `WHERE`, `JOIN`, `GROUP BY` and `ORDER BY` only compare columns with values of the same kind. MariaDB answers, among others:

- a computed result column: `SUM`, `AVG`, `ROUND`, `CONCAT`, arithmetic, `JSON_EXTRACT`, a `CASE`, any function but `COUNT`;
- `UNION`, a window function, a variable, a bit operator, `/` between two numbers, decimal arithmetic;
- a text column compared with a number, a number column compared with text, a date column compared with a number;
- an `ENUM`, `SET`, `BIT`, `BLOB` or `FLOAT` column grouped, sorted or compared;
- text with accents or a trailing space, in the statement, in a value bound to it, or in a text column it compares (a write that puts such text in a column is noticed at once).

The rules look at the statement's shape, each column's declared MariaDB type and the values bound. They never name a table, a column or a resource, so a renamed table or a new resource is judged the same way. `tests/repro/maria_trust.js` checks every rule against MariaDB with oxmysql's own pool options and `typeCast`.

Before MariaDB answers a read, writes to the tables it reads that are still in the outbox are copied, so the read sees every write SQLite already took. If MariaDB is down, the copy is behind by more than 10 seconds, or MariaDB does not answer within `cis_database_maria_read_ms` (30 s), the read fails with the reason, for example `this read is answered by MariaDB (computed column SUM ( amount )) and MariaDB failed: ...`. It is never answered from SQLite instead. Reads SQLite answers keep working during the outage, and writes keep going to SQLite and the outbox. A write is never timed out, since MariaDB may still commit it.

Reads inside a transaction stay on SQLite, so they see the transaction's own writes.

With the `sql.js` fallback the database lives in memory and is loaded from the snapshot of an earlier boot, which lacks the writes since. If MariaDB does not answer at boot, the resource waits for it as on a first install instead of starting from that snapshot.

With no MariaDB configured, SQLite answers everything it can run. A read it cannot run fails with SQLite's error and ` (no MariaDB is configured to answer this read)`, never with a value. The differences listed in [SQL-DIALECT.md](SQL-DIALECT.md) then apply to the reads above as well.
