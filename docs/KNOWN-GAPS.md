# Known gaps

- `startTransaction` is not supported yet. oxmysql's `MySQL.startTransaction(function(query) ... end)` keeps one connection open while the function awaits each query. cis_database has one SQLite connection, which other resources and the MariaDB copy also write on between those awaits, so it cannot hold a transaction open that way without other writes landing inside it. The export exists, runs nothing, prints the reason once per resource and returns `false`, which callers treat as a failed transaction. Use `MySQL.transaction` with the list of queries instead.
- SQLite has no exact decimal type, so a `DECIMAL` is kept as a 64-bit float. Values with up to 15 significant digits (`DECIMAL(15,2)` covers 9,999,999,999,999.99) come back exact; a `DECIMAL(20,0)` value such as 12345678901234567 comes back as 12345678901234568. With MariaDB configured, MariaDB keeps the exact value, and reads that compute on a `DECIMAL` (arithmetic, `ROUND`, `CONCAT`) are answered by MariaDB. With SQLite alone, such arithmetic returns a number with the float's rounding (a `0.10` times 3 gives `0.30000000000000004`) where MariaDB returns `'0.30'`; `SUM`, `AVG`, `MIN` and `MAX` of a column are formatted as MariaDB's (see [SQL-DIALECT.md](SQL-DIALECT.md)). Storing every `DECIMAL` as text with exact arithmetic would need a decimal library in every SQLite expression; that is not planned for 1.0.
- The corpus run (`tests/corpus/match.js`, see [SQL-DIALECT.md](SQL-DIALECT.md): 3,016 statements from 154 public resources, each run on cis_database and on MariaDB 10.11; local run of 2026-11-01, no output file is kept, rerun it with `node tests/corpus/match.js`) still finds 51 statements that answer differently. 24 are rows whose values differ: 22 are `NOW()` and `CURRENT_TIMESTAMP` values the two runs took one to three seconds apart, and 2 are `DATABASE()`, which names each run's own test database. 21 are writes MariaDB's strict mode refuses that SQLite takes, all with values the run made up (`'v1'` into an `INT`, `DECIMAL` or `DATETIME` column), plus one foreign key to a missing row, one mix of collations and one missing default; on a live server MariaDB refuses its copy of such a write, the refusal is counted on the dashboard (`replica_drop`) and logged, and the game keeps the row only until the next start: that boot copies the table again from MariaDB, which never had the row. Fix the column type or the value in the resource that writes it. 3 are `REPLACE` of a row that already existed, which MariaDB counts as 2 rows (one deleted, one inserted) and cis_database as 1; the data is the same. 3 are an `insertId` one lower than MariaDB's, after an earlier statement in the same run that only MariaDB had spent an id on.
- With the `sql.js` fallback the database is in memory. A write is answered before anything is on disk, and its only durable copy is MariaDB's, sent about every 50 ms. A crash of the server process loses the writes MariaDB had not received yet: the last 50 ms or so with MariaDB up, every write since MariaDB went down otherwise. No test can show sql.js keeping an answered write through a crash, because it does not. `node:sqlite` (the default on FXServer 35245+) has none of this: see [HOW-IT-WORKS.md](HOW-IT-WORKS.md).
- An edit made directly in MariaDB while the server runs (a web panel, HeidiSQL) reaches the game copy at the next scan. A scan runs after 2 s with no query, and every 10 s whatever the load (`cis_database_cdc_force_ms`). A forced scan gives up a table the game writes while it copies that table, so a table the game writes every few seconds can keep the old row until a scan gets through or the next start. An edit made while the server is stopped is always in: every boot copies again each table whose MariaDB checksum, columns or indexes changed, except a table with writes still waiting for MariaDB, which is copied once they are in.
- A row inserted directly in MariaDB while the server runs gets an id far above the game's. The resource keeps MariaDB's `AUTO_INCREMENT` for each table 1,000,000 above the highest id SQLite has given out (`cis_database_id_gap`; less for a small integer type), checked every 5 s. This needs the `ALTER` privilege on the game database; without it the log says so once, and a hand-made insert can take the id of the game's next insert, which MariaDB then refuses. Any write MariaDB refuses as a duplicate key is logged as a warning and counted in the dashboard. Hand-made rows end up with high ids, and once such a row is copied the game's own ids carry on above it. The game would reach a hand-made row's id only after it inserted 500,000 rows into that table before the next scan. `auto_increment_increment` and `auto_increment_offset` are not used: they are server-wide or per session, and a panel's session is not this resource's to set.
- A big import sent as one statement (a seed file or a dump with thousands of rows in a single `INSERT`) is never split, so it can still take one long frame: splitting it across slices would let other calls see half of it, and a statement must be all or nothing. The console names any statement, transaction or `execMany` list that held the server thread for 50 ms or more. Send a big import as several calls, or run it while the server is empty. SQLite's checkpoint copies every WAL frame written since the last pass in one call and cannot copy part of them; the longest copy on the benchmark VPS was 22.6 ms (benchmark VPS run, 2026-11-01, local).
- A MariaDB executable comment (`/*! ... */`, `/*!50100 ... */`) is an ordinary comment to cis_database: SQLite skips it and the copy sent to MariaDB leaves it out, so the code inside runs on neither side. With oxmysql, MariaDB would run it. Do not put executable comments in game SQL. A statement whose own text holds a `;` or a comment (outside its strings) is copied to MariaDB on its own, on a connection that runs one statement per call, so MariaDB never decides where it ends.
- A write reaches MariaDB with the clock of the moment the game made it. `NOW()`, `CURRENT_TIMESTAMP` and `ON UPDATE CURRENT_TIMESTAMP` give MariaDB the same time as SQLite, even when MariaDB was away and the write waited in the outbox (the two still differ by any time-zone gap, which the console warns about at start). `UUID()`, `UUID_SHORT()` and `RAND()` in an `INSERT` or `REPLACE ... VALUES` are made once and sent to both copies as the same value. Elsewhere MariaDB computes them again, so the two copies hold different values: in `UPDATE`, `INSERT ... SELECT`, `ON DUPLICATE KEY UPDATE`, and in a column `DEFAULT UUID()` that the `INSERT` leaves out. A value sent there as one literal would give every row the same value. Make such values in the resource and pass them as parameters.
- A table the game wrote is copied from MariaDB once more: by the change scan after the write's quiet window, or at the next start. The copy holds the same rows, so nothing changes in the game, but a big table costs its copy time. The resource cannot skip it safely. MariaDB's `CHECKSUM TABLE` after the game's writes would also count an edit someone made in MariaDB to that table in the meantime, and recording it as "the game copy holds these rows" would keep that edit out of the game for good.
- The header `query` and `rawExecute` hand back for an `UPDATE` counts a row set to the value it already had as changed: `changedRows` and the `Changed:` part of `info` equal the matched rows. SQLite reports only how many rows the `WHERE` matched. MariaDB counts such a row as matched but not changed. `affectedRows`, the number oxmysql's `update` returns, matches oxmysql: mysql2 asks MariaDB for matched rows.
- When an `fdatasync` of the WAL fails, the writes waiting for it stay unanswered until a later sync succeeds, so scripts wait as long as the disk keeps failing. On Linux a sync that succeeds after a failed one may not cover pages the kernel already dropped after the failure, so a write answered then can still be lost to a power cut. `cis_database_doctor` shows a FAIL from the first failed sync until the next start; replace or repair the disk.
- A change scan reads a table from MariaDB 500 rows at a time. A table with a primary key is read in key order, each page starting after the last key read. A table without a primary key is still read with `LIMIT 500 OFFSET n`, so MariaDB walks past every earlier row for each page, and copying such a table of a few hundred thousand rows costs far more than its size suggests. It runs in the background and only for a table MariaDB changed from outside the game.
- While MariaDB refuses writes with an error that usually passes (read-only, disk or table full, see CHANGELOG 1.0.0), the outbox holds the refused entry and every entry after it, and retries every few seconds with a warning on the 1st and every 20th try. If the cause never passes (a table that has hit its size limit), the replica stays behind until it is fixed; the writes are kept in SQLite, not dropped.
- A MariaDB column whose name is not letters, digits, `_` and `-` (a space, a non-ASCII letter) is not copied into SQLite, and a script cannot read or write it through this resource. The copy logs a warning naming it. Rename it in MariaDB to use it.
