# SQL dialect

How MySQL statements are translated to SQLite, how the result is checked against MariaDB, and where the two still differ.

Scripts write MySQL. Each statement is translated to SQLite once and the translation is kept in memory. `tests/repro/dialect_market.js` runs the SQL of es_extended, qbx_core, ox_inventory, ND_Core and common phone, garage, housing and banking scripts through it against a real SQLite database and checks every result against MariaDB answers recorded in the test. Across public resources, `tests/corpus/` takes 154 repositories at pinned commits (`tests/corpus/repos.json`) and runs every SQL statement they contain twice: once through cis_database and once on MariaDB 10.11.19 itself, through mysql2 with oxmysql's own pool options and type casting, on the same schema, rows and params. 98.31 % of compared statements (2965 of 3016) give the same answer on both sides, and 141 of the 154 repositories match on every statement (local run of 2026-11-01; no output file is kept, rerun it with the two commands below). The translator turns 98.30 % of the statements it scores (3130 of 3184) into SQLite. To run it yourself, start a throwaway MariaDB 10.11 on `127.0.0.1:3307` with root and no password (the harness creates and drops `cm_ref` and `cm_eng` there), then:

```
node tests/corpus/translate.js
node tests/corpus/match.js
```

`match.js` prints each kind of difference with sample statements; the main ones left are listed in [KNOWN-GAPS.md](KNOWN-GAPS.md). The differences known so far are listed below.

- `INSERT ... ON DUPLICATE KEY UPDATE`, with `VALUES(col)`, updates the existing row when any primary or unique key clashes, as MariaDB does. The row keeps its id and every column the statement does not set, and the affected count is 1 for an inserted row, 2 for a changed one and 1 for a row found with nothing to change, as oxmysql reports them. `INSERT IGNORE`, `REPLACE INTO` and `INSERT ... SET` work too. An insert into a table with no AUTO_INCREMENT key reports id 0. An insert of several rows whose ids are generated reports the first new row's id, in `insertId` and in `LAST_INSERT_ID()`, as MariaDB does.
- `UPDATE` and `DELETE` with `ORDER BY ... LIMIT n` change exactly those rows. `UPDATE a JOIN b ... SET` and `DELETE a FROM a JOIN b` change the rows MariaDB changes, with each value on its own `?`.
- DDL: `CREATE TABLE` with the clauses MariaDB dumps carry (`AUTO_INCREMENT` beside another primary key, `ON UPDATE CURRENT_TIMESTAMP`, generated columns, `CHECK`, `FULLTEXT` and expression defaults such as `JSON_OBJECT()`), `ALTER TABLE` with several clauses, `DROP`, `RENAME` and `CREATE INDEX`. Foreign keys cascade and refuse as InnoDB's do, including a key to a column that is not unique (ox_mdt, ps-mdt). Tables copied from MariaDB get the same.
- `information_schema` (`TABLES`, `COLUMNS`, `STATISTICS`, `TABLE_CONSTRAINTS`, `KEY_COLUMN_USAGE`, `REFERENTIAL_CONSTRAINTS`, `SCHEMATA`), `SHOW TABLES`, `SHOW COLUMNS`, `SHOW INDEX` and `DESCRIBE` answer from SQLite with MariaDB's column types (`varchar(46)`, `enum(...)`, `decimal(10,2)`), taken from MariaDB when a table is copied and from the DDL when a script creates one. The query runs as written, so migrations that decide what to `ALTER` from these answers see what MariaDB would tell them. `tests/repro/info_schema.js` checks each answer against MariaDB's.
- A result column is named as the SELECT writes it: `SELECT stateId` on a column declared `stateid` gives `row.stateId`, and ``COUNT(`id`)`` is the key ``COUNT(`id`)``. `DATABASE()` is the configured database and `VERSION()` MariaDB's version.
- A value comes back in the type oxmysql gives it, decided by the declared type of the column it is read from (an alias or a join keeps it): `DATETIME` and `TIMESTAMP` as epoch milliseconds, `DATE` as milliseconds at local midnight, `TINYINT(1)` and `BOOLEAN` as `true` or `false`. `MySQL.prepare` and `rawExecute` turn the dates only, so `TINYINT(1)` stays `1` or `0` there, as oxmysql's `execute` path does. The types are MariaDB's for a copied table and the DDL's for a table a script creates. `tests/repro/type_casts.js` checks both against a real MariaDB.
- `'...'` and `"..."` are both strings, with MySQL's backslash escapes (`\n`, `\t`, `\'`, `\\`). `\%` and `\_` keep their backslash, and a backslash in a `LIKE` pattern escapes the next character, as in MySQL. Backticks quote names. Text inside a string literal is never rewritten.
- Dates: `NOW()`, `CURDATE()`, `CURRENT_TIMESTAMP()`, `DATE_ADD`, `DATE_SUB`, `ADDDATE`, `SUBDATE`, `expr + INTERVAL n unit` and `expr - INTERVAL n unit` (units SECOND to YEAR, WEEK and QUARTER; `n` may be `?`), `TIMESTAMPDIFF` (SECOND to WEEK), `TIMESTAMPADD`, `DATEDIFF`, `UNIX_TIMESTAMP`, `FROM_UNIXTIME`, `DATE_FORMAT` with numeric specifiers and English month and day names (`%M`, `%b`, `%W`, `%a`, `%y`), `STR_TO_DATE` with numeric specifiers, and `YEAR()` through `SECOND()`. They use the server's local time, as MariaDB does with its default `time_zone` (`SYSTEM`): `NOW()`, `CURDATE()`, a `DEFAULT CURRENT_TIMESTAMP`, an `ON UPDATE CURRENT_TIMESTAMP` stamp, `UNIX_TIMESTAMP` and `FROM_UNIXTIME`. If MariaDB's `time_zone` is set to another offset than the server's clock, the two disagree by the gap, and cis_database says so in the log at boot.
- `HAVING` with no `GROUP BY` and no aggregate filters rows the way MariaDB does, select aliases included.
- JSON: `JSON_EXTRACT`, `JSON_UNQUOTE`, `JSON_VALUE`, `JSON_SET`, `JSON_CONTAINS`, `JSON_LENGTH` and the rest of the common set. `col->'$.path'` and `col->>'$.path'` become `json_extract`. When `JSON_EXTRACT(doc, path)` or `col->'$.path'` is a whole column of the SELECT, a JSON `true` or `false` comes back as a Lua boolean, as it does from MySQL, so `if row.isdead then` is false for `false`. In a `WHERE` or inside another call it stays `1` or `0`, so `= true` and `= 1` both match.
- Other functions: `IFNULL`, `IF`, `CONCAT`, `GREATEST`, `LEAST`, `FIND_IN_SET`, `FIELD`, `LEFT`, `RIGHT`, `LOCATE`, `LPAD`, `RPAD`, `SUBSTRING_INDEX`, `TRUNCATE`, `UNHEX`, `MD5`, `SHA2`, `REGEXP`, `RLIKE`, `LAST_DAY`, `GROUP_CONCAT` with `DISTINCT`, `ORDER BY` and `SEPARATOR`, and `LAST_INSERT_ID()`. `REGEXP` runs in linear time; one statement gets about 50 million matcher steps across all its rows (roughly a second), and past that it fails with `REGEXP: statement matched too much text to finish safely` instead of holding the server thread. `BINARY x` and `COLLATE ..._bin` compare byte for byte. `STDDEV` and `VARIANCE` work when the runtime's `node:sqlite` has aggregate functions. Index hints (`USE INDEX`, `FORCE INDEX`, `IGNORE INDEX`), `FOR UPDATE` and `LOCK IN SHARE MODE` are dropped. They never change a result.

A statement with no exact SQLite form is never turned into something close. Examples are a day-of-month suffix (`%D`) in `DATE_FORMAT`, `TIMESTAMPDIFF(MONTH, ...)`, `CONVERT_TZ`, `DIV` and a compound `INTERVAL` unit. SQLite refuses the statement. A read is then answered by MariaDB, and that statement goes straight to MariaDB from then on. A write fails for its caller.

Statements with nothing to do on SQLite answer success and change nothing: `SET NAMES` and other session settings, `USE`, `LOCK TABLES`, `UNLOCK TABLES`, `START TRANSACTION`, `BEGIN`, `COMMIT` and `ROLLBACK` sent alone (use `transaction` for a transaction; a `COMMIT` inside its list does not end it), `CREATE DATABASE`, and `DROP` of a procedure, function, trigger or event. `ALTER VIEW` replaces the view, as `CREATE OR REPLACE VIEW` does. Statements that do real work on MariaDB and have no SQLite form fail with a `cis_database:` message, and neither database runs them: `CALL`, `SIGNAL`, `SET @name` (SQLite has no user variables), `CREATE` or `ALTER` of a procedure, function, trigger or event, `CREATE OR REPLACE TABLE`, a `TRUNCATE` of more than one table, and an `UPDATE ... SET ?` whose value is not a table of column names, has no keys, or has a key that is not a plain column name.

Strict mode is mirrored from the replica's `sql_mode` (MariaDB's default, `STRICT_TRANS_TABLES`, until MariaDB has been reached once). A value its column cannot hold is refused with MariaDB's message (`Out of range value`, `Data too long`, `Data truncated`, `Incorrect integer value`, and `Incorrect string value` for an emoji or other character past U+FFFF in a `utf8mb3` column, or past U+007F in an `ascii` one), and so is an `INSERT` that leaves out a `NOT NULL` column with no default (`Field 'x' doesn't have a default value`). The write then reaches neither database. A value MariaDB takes is stored as MariaDB stores it: a real rounded to an integer column or to a `DECIMAL`'s scale, an `ENUM` value in the type's spelling or by its position, trailing spaces cut past a `VARCHAR`'s length. Under `INSERT IGNORE`, `UPDATE IGNORE` or a `sql_mode` that is not strict, a number is clamped to its type's range, a string cut to its column's length, an unknown `ENUM` value stored as `''`, and a missing `NOT NULL` column as `''` or `0`. Triggers named `cis_strict:` do this; they call functions only cis_database registers, so a database file written by this version needs this version or a later one.

SQLite keeps a `DECIMAL` as a 64-bit float (`REAL`). A value is rounded to its column's scale when it is written, and comes back as the string mysql2 gives under oxmysql, with exactly that many places (`'0.10'`). `SUM`, `MIN` and `MAX` of one `DECIMAL` column come back the same way at the column's scale, and `AVG` at the scale plus 4 (`'0.150000'`), as MariaDB gives them; `tests/repro/decimal_aggregates.js` checks them. Other arithmetic on a `DECIMAL` (`price * 3`) comes back as a number with the float's rounding when SQLite answers it; when MariaDB is configured, it answers those reads (see KNOWN-GAPS.md).

Text in a `utf8mb4_general_ci` or `utf8mb4_unicode_ci` column (or their `utf8mb3` forms) sorts and compares as MariaDB does. `ORDER BY` such a column (by its name, an alias or its position) goes through `cis_ci()` or `cis_uci()`, which turn the text into MariaDB's weights for that collation. So do `<`, `>`, `<=`, `>=` and `BETWEEN` against a string, a `?` or another column of the same collation. In `general_ci` letters fold to upper case, so `[`, `_` and `~` sort after them. In `unicode_ci` (UCA 4.0.0) punctuation sorts before digits and digits before letters, and `ß` sorts as `ss`. In both, most accented letters fold to their base letter, and trailing spaces do not count. Equality uses SQLite's `NOCASE`, which an index can serve. Every `_ci` text column compares without case, whether it was copied from MariaDB or created by a script, and a `_bin` or `JSON` column compares with case. A sort through `cis_ci()` or `cis_uci()` cannot read an index in order, so `ORDER BY name LIMIT 10` with no `WHERE` reads the whole table: about 10 to 30 ms for 50,000 rows.

Where SQLite still answers differently from MariaDB:

- `JSON_EXTRACT` returns values, not JSON text: a number is a number and a string comes back without its quotes. MariaDB returns JSON text (`"Bob"`, `50`, `true`). An object or array comes back as JSON text on both.
- `/` between two integers divides as integers in SQLite: `5 / 2` is `2`. MariaDB returns `2.5000`.
- `=` between texts ignores ASCII case only, so `'é' = 'E'`, `'ß' = 'ss'` (in `unicode_ci`) and `'a' = 'a '` are true in MariaDB and false here. `MIN`, `MAX`, `GROUP BY` and `DISTINCT` on text compare the same way.
- Columns in the other UCA collations (`utf8mb4_unicode_520_ci`, `utf8mb4_uca1400_ai_ci` and the language ones) and in `latin1_swedish_ci` compare without case but sort by byte.
- A value ending in a character that sorts before a space (a tab, a newline) sorts after the same value without it; MariaDB sorts it first.
- A text column a script created with `CREATE TABLE` under an earlier version compares with case.
- `ORDER BY` an `ENUM` column sorts by the text. MariaDB sorts by the value's position in the type.
- A value MariaDB's strict mode refuses only inside a function or a comparison (a `DECIMAL` cut short in `FROM_UNIXTIME('2024-01-01 10:00:00')`) is taken by SQLite; MariaDB's copy of that write then fails and is logged.
- A date or `TINYINT(1)` value computed by an expression (`MAX(created)`, `IFNULL(seen, NOW())`, `NOW()`) is not read from a column, so it comes back as SQLite gives it: a `'YYYY-MM-DD hh:mm:ss'` string or `1` / `0`. MariaDB types it and oxmysql casts it. A `BIT` column comes back as a number, not oxmysql's boolean.
- The `CHECK` MariaDB adds to a `JSON` column is not listed in `information_schema.TABLE_CONSTRAINTS`, and `SHOW INDEX` has no `Cardinality`.
