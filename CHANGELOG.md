# Changelog

## 1.0.0 (2026-11-25)

- The `/cis_db` panel has the Cisoko look of the other resources: a dark glass window, a tab bar and status chips, with Inter and JetBrains Mono shipped in the resource (`web/dist/assets`, their SIL Open Font License texts in `web/dist/licenses`). It loads nothing from outside the resource, and what it shows is unchanged.
- A player without the ACE who types `/cis_db` is told why: `no permission: needs ace cis_database.dashboard` in chat and in F8. Before, nothing happened. Grant it with `add_ace group.admin cis_database.dashboard allow` in `server.cfg` (README, API.md). A panel closed because the resource stopped prints nothing.
- The replica no longer drops writes while MariaDB is read-only or out of space. An outbox entry MariaDB refused with an error that passes on its own (1290 `--read-only`, 1792 read-only transaction, 1836 read-only mode, 1021 disk full, 1114 table full, 1053 server shutdown, 1927 connection killed) was logged as a refused statement, marked applied and removed, so MariaDB lost every write made while the error lasted. Those entries now stay in the outbox and are sent again with backoff.
- Copying a MariaDB table with a column whose name this resource cannot use in SQL (a space, a non-ASCII letter) no longer fails the whole copy. The column was left out of the SQLite table but still listed in each copied row, so every row failed, and a first install retried the copy forever while reporting that MariaDB did not answer. The column is now left out of the copy too, with a warning that names it.
- The statement guard refuses `VACUUM` with a schema name before `INTO` (`VACUUM main INTO 'file'`, quoted or bracketed names too). It refused only `VACUUM INTO`, so a statement that reached the resource could write a copy of the whole database to a file it chose.
- Change Data Capture no longer deletes child rows in SQLite. When it copied a table MariaDB changed outside the game, it wrote each row with `INSERT OR REPLACE`. On a key SQLite already had, REPLACE deletes the old row first, and with foreign keys on that delete ran every child table's `ON DELETE CASCADE`. On Qbox a copy of `players` deleted every `player_vehicles`, `player_groups` and `player_jobs_activity` row in SQLite, while MariaDB kept them; a copy of `player_vehicles` did the same to `vehicle_financing`. The copy now updates the row in place (`INSERT ... ON CONFLICT DO UPDATE`). A row whose other unique key (a plate) still belongs to a row MariaDB deleted is copied once the copy has removed that row, in the same pass; a row that still clashes is left as it is, the copy is retried on the next change check, and a warning with the error prints at most once a minute per table. A copied row keeps MariaDB's `ON UPDATE CURRENT_TIMESTAMP` value.
- Change Data Capture no longer misses a row MariaDB still has. It read a changed table in pages of 500 with `LIMIT ... OFFSET` and no `ORDER BY`, then removed every SQLite row no page returned. Without an order, two pages may overlap and leave a row out, and on a MyISAM or Aria table (no consistent snapshot) a row deleted between two pages shifted the next page past a live row. The missed row was deleted in SQLite, with its child rows through `ON DELETE CASCADE`. A table with a primary key is now read in key order, each page starting after the last key read. A table without a primary key is read as before.
- The admin panel can reach its callbacks again. Its page allowed fetches only to `https://cis_database`, but a host with `_` is not a valid CSP source, so the game browser dropped it, allowed no fetch at all and printed an "invalid source" error. The page now allows `https:` fetches; it still loads scripts and styles only from its own files.
- `MySQL.prepare` and `MySQL.rawExecute` given a list of parameter lists run the statement once per list, in order, as oxmysql does. es_extended adds its items at boot so (`INSERT IGNORE INTO items ... VALUES (?,?,?,?,?)` with one list per item), and ox_inventory saves its stashes so. Before, es_extended's call failed with `Expected 5 parameters, but received 15.` and `esx_shops` stopped with a script error, and `rawExecute` did not run once per list. `prepare` returns the insert id or the rows changed of each list, `rawExecute` the header or the rows of each; a batch runs on SQLite only ([API.md](API.md)).
- `MySQL.prepare` answers as oxmysql does: a read of several rows returns the rows, and an `INSERT` returns the insert id. Before, a read of several rows returned the first value of the first row and an `INSERT` returned the rows changed. A new test runs 131 call shapes of oxmysql 2.14.3 through `MySQL.*` in `lib/MySQL.lua`, the `_async` and `Sync` exports and the mysql-async and ghmattimysql names, and another covers every path that fits a value list to its placeholders, on SQLite and on the MariaDB copy.
- The first boot line names the build and what it stands in for: `cis_database 1.0.0 provides oxmysql 2.14.3, mysql-async and ghmattimysql`. README and docs/INSTALL.md now say where `ensure cis_database` goes when a recipe starts oxmysql through a category (QBCore's `ensure [standalone]`), that the `oxmysql` folder must leave every category `server.cfg` starts, and which two tables cis_database adds to MariaDB.
- The README figures and the p99 chart come from a new 5-round benchmark of this build on 2026-11-02 (`bench/results/2026-11-02-8c73b74-frame25`; `8c73b74` labels a pre-release build of this code, not a commit in this repository). The "Is it worth installing?" table now also shows the idle server tick and memory.
- The slice wake sockets on 127.0.0.1 take a wake only from each other; a datagram another local process sends to their port is ignored. The release zip ships only the sql.js build cis_database loads (`dist/sql-asm.js`) and no type packages (`@types/node`, `undici-types`). `npm test` gives each check its own temp directory and removes it after.
- `SUM` of an integer column comes back as a string, as mysql2 gives MariaDB's `DECIMAL(n,0)` (`'6'`), and `AVG` with four places (`'2.0000'`). `MIN`, `MAX`, `COUNT` and plain reads stay numbers. Before, SQLite answered numbers, so code that compared `SUM(money)` with a string or called `string.len` on it behaved differently on cis_database.
- One call runs one statement, as in oxmysql. A text with a second statement after a `;` is refused with `ER_PARSE_ERROR` and nothing of it runs. Before, cis_database ran every statement, so a value a resource concatenated into its SQL (`x'; UPDATE users SET money = ...`) ran its own statement, where oxmysql's MariaDB refused it. `cis_database_multi_statements true` allows several statements again, the same opt-in as oxmysql's `multipleStatements`. A `;` inside a `` `name` `` or a comment no longer splits a statement.
- `lib/MySQL.lua`, the include scripts load as `@oxmysql/lib/MySQL.lua`, is rewritten from oxmysql's documentation by someone who had not read oxmysql's include. A callback that arrives from another resource as a function reference is taken as a callback in both positions. `MySQL.<name>` reaches any other export of the driver (`MySQL.isReady()`, `MySQL.awaitConnection()`). `MySQL.store`, `MySQL.startTransaction` and `MySQL.ready` each have `.await`. A query that is not a string raises in the caller with what arrived.
- A write that waited in the outbox reaches MariaDB with the clock of the moment the game made it: replay sets MariaDB's session `timestamp` to SQLite's commit time and resets it after, so `NOW()`, `CURRENT_TIMESTAMP` and `ON UPDATE` columns match. Before, a ban written with `NOW() + INTERVAL 1 DAY` while MariaDB was away expired that much later in MariaDB. `UUID()`, `UUID_SHORT()` and `RAND()` in an `INSERT ... VALUES` are made once and bound as the same value on both sides, so a row keyed by `UUID()` has the same key in MariaDB; other places are listed in docs/KNOWN-GAPS.md.
- A failed query no longer calls a plain callback with `false`, as in oxmysql: the error is printed in the server console, with the resource and the statement. Before, `MySQL.scalar(sql, p, function(money) if not money then ... end end)` ran its "no row" branch on any error. A resource with `mysql_option 'return_callback_errors'` in its fxmanifest gets the callback as `(nil, message)`, oxmysql's opt-in.
- `execMany` and `queryMany` take the list as their first argument, or as the second after a `nil`, and raise in the caller when neither is a list. API.md showed `execMany(nil, { ... }, cb)`; that call passed the list where the callback goes, so nothing ran and nothing said so.
- A statement, a transaction, an `execMany` list or a WAL checkpoint copy that holds the server thread for 50 ms or more prints one warning with its caller and its SQL, every quoted string and number shown as `?`, at most one line of each kind every 10 s. One statement is never split, and before, a hitch it caused named nothing. HOW-IT-WORKS no longer says a checkpoint copy takes about a millisecond: the longest on the benchmark VPS took 22.6 ms.
- `MySQL.store` hands back a number, as oxmysql's include does, and any later `MySQL.*` call takes it in place of the SQL. `awaitConnection()` returns `true` once the engine answers calls, to a waiting thread or to its callback; before, it returned nothing at once. `MySQL.ready(cb)` starts its wait with `Citizen.CreateThreadNow` (FiveM has no global `CreateThreadNow`), so when the engine is up `cb` runs before the call returns.
- `CREATE TABLE` of a table that exists, `ADD COLUMN` of a column that exists, and `CREATE INDEX` or `ADD INDEX` of an index name the table has now fail as on MariaDB (`Table ... already exists`, `Duplicate column name`, `Duplicate key name`), and `ADD PRIMARY KEY` on a table that has one fails with `Multiple primary key defined`. They used to report success. The `IF NOT EXISTS` forms still succeed.
- A failed `fdatasync` of the WAL no longer answers the writes it was for or sends their rows to MariaDB. The sync is retried after 1 s, doubling to 30 s, and the first one that succeeds answers them. A failed sync at stop leaves its writes unanswered. `cis_database_doctor` shows a FAIL for disk sync once any sync has failed.
- The header `query` and `rawExecute` hand back for an `UPDATE` now carries `changedRows` and MariaDB's `info` line (`Rows matched: n  Changed: n  Warnings: 0`). Other statements keep `changedRows` 0 and an empty `info`.
- `CALL`, `SIGNAL`, `SET @name`, `CREATE` or `ALTER` of a procedure, function, trigger or event, `CREATE OR REPLACE TABLE`, a `TRUNCATE` of several tables and an `UPDATE ... SET ?` left without its table of columns now fail with a reason. Before, each was answered as if it had run and did nothing on SQLite, and `CREATE TRIGGER` still reached MariaDB. A refused statement is never sent to MariaDB as a read either.
- A `COMMIT` or `ROLLBACK` inside a `transaction` list no longer ends the transaction cis_database holds. Before, the statements before it were kept when a later one failed. Sent alone through `query`, `COMMIT` and `ROLLBACK` answer success like `START TRANSACTION`, instead of an error.
- `UPDATE ... SET ?` with a key that is not a plain column name, or with no keys, fails. Before, such a key was dropped and the rest of the UPDATE ran.
- `--` followed by a character other than a space or a control character is two minus signs everywhere, as in MySQL: `SET v = 1--?` is `1 - (-?)`. Before, the MariaDB copy, `IN (?)` lists and `UUID()` binding read it as a comment, so the copy lost the rest of the line and MariaDB missed the write.
- `CONCAT('a', 1 + 2)` returns `a3`. Before, an argument with `+` or `-` was split by SQLite's `||` precedence and the result was a number.
- `ALTER VIEW` replaces the view's query, as `CREATE OR REPLACE VIEW` does. Before, it did nothing on SQLite.
- With SQLite alone, `SUM`, `AVG`, `MIN` and `MAX` of a `DECIMAL` column return the string MariaDB gives through oxmysql (`'0.30'`, and `AVG` with 4 more places), not a float such as `0.30000000000000004`.
- A call with more values than its SQL has `?` marks fails with oxmysql's `Expected 1 parameters, but received 2.` and runs nothing; an `IN (?)` list counts as one mark. Before, it failed with SQLite's `column index out of range`, and such a read went on to MariaDB, which ignored the extra values and answered. A statement with no mark ignores its values, as in oxmysql; before, it failed.
- A MariaDB table named `audit_log`, or one whose name ends in `_bench`, is copied, scanned for edits and kept in the id reserve like any other table. Before, all three left it out, so every game write to it failed with `no such table`. Only cis_database's own `__cis_` tables are left out.
- A value that holds the word `attach`, `detach`, `load_extension(`, `vacuum into` or `__cis_`, such as a note reading "please attach the file", is stored like any other. Before, the statement failed with `blocked SQL`. The words are still refused in the SQL itself, and a quoted function name such as `"load_extension"(...)`, which SQLite calls, is now refused too.
- A backslash-escaped quote inside a string (`'I\'m #1'`) no longer ends it for the comment remover. Before, a `#`, `-- ` or slash-star after it opened a comment that took the rest of the statement, its WHERE clause included.
- An `INSERT ... ON DUPLICATE KEY UPDATE` that inserts reports affectedRows 1 and the new id on a fresh table too. Before, when the new row got the same number as the outbox row of the previous write, it was taken for an update: insertId 0, affectedRows 2, and the MariaDB copy was sent without the id SQLite used.
- A Lua table with a key above 65535 used as a parameter list, an `IN (?)` list, a `transaction` list or an `execMany` list is refused with the reason. Before, `{ [2000000000] = 'x' }` built an array with a slot for every number up to its key on the server thread and ran the server out of memory. `{ nil, 'b' }` still binds `NULL, 'b'`. An `execMany` item's `kind` must be one of `query`, `insert`, `update`, `scalar`, `single`, `prepare` or `rawExecute`.
- The change copy of a table no longer deletes a row the game wrote while the copy waited for MariaDB's last page. Only the copy a busy server forces checked for such a write before the delete; every copy now gives the table up and tries again later.
- A list bound to a `?` inside `IN ( )` expands however the list is written: `IN ('a', ?)`, a `(` or `?` inside a string in the list, and a list longer than 200 characters. Before, each of these bound the list as one value and matched nothing. A `?` in a subquery or a call inside the `IN` stays one value, as before.
- A statement whose own text holds a `;` or a comment is copied to MariaDB on its own, on a connection that runs one statement per call, so MariaDB never decides again where it ends.
- The per-frame tick runs as a `setTick` in the engine's own JavaScript, not as a Lua `Wait(0)` thread that called into it every server tick. On the benchmark VPS that thread and its export call cost 0.23 ms of the resource's 0.36 ms per idle frame.
- A boot copies from MariaDB only the tables MariaDB changed. Each copy records MariaDB's `CHECKSUM TABLE` and the table's shape. A table where both still match is kept. Before, every boot copied every table: about 22 s and 10 to 17 server hitches of 150 to 480 ms on the benchmark VPS. On a local test with 114 tables and 92,000 rows, a boot with nothing changed now takes 0.3 s, against 3.7 s before (local run, 2026-10-28; no result file is kept).
- A table that is copied is emptied and filled in place in small steps, with the server thread handed back between them, instead of through a staging table and a rename. No step held the thread for 100 ms or more in that test.
- The boot copy checkpoints the WAL with the same split cycle as the running server, its syncs on the thread pool. Before, a checkpoint during the copy ran on the server thread with both syncs, and a first boot that copied every table held the thread for 113 to 199 ms once in some runs. In the same test the first boot's longest pause is now 32 to 44 ms over 6 runs, and the copy takes about 1.8 s instead of 2.5 s.
- The boot copy starts the WAL over as it goes. Before, its rows all stayed in `cache/durable.sqlite-wal`, so a server stopped without a clean close (killed, crashed, closed from its window) replayed the whole copy on the server thread at the next start. In a test with 160,000 rows, a killed cold boot left 139,076 WAL frames and the next start's load took 411 ms; it now leaves 50 frames and the next load takes 30 ms.
- The boot copy hands the server thread back once it has worked for a frame, not after every 100 rows. FXServer runs Node once per server tick, so each hand-back waited a tick: a first boot on the benchmark VPS took 61 s to copy 92,189 rows. In a local test with 165,500 rows the copy now hands the thread back 293 times instead of 2,203 (local run, 2026-10-28; no result file is kept).
- The boot steps after the copy (the strict-mode triggers of every table, `ANALYZE`, the column types) share the frame budget with the copy, and hand the thread back before a step that would run past the frame. Before, they kept their own 25 ms clock on top of the copy's work and checked it only after a step: the end of a cold boot on the benchmark VPS ran 25 to 30.5 ms ticks, 38 ms locally. Locally the longest turn there is now 13 to 22 ms.
- An idle server starts its WAL over once every frame is copied. Before, the frames of the last burst of writes stayed valid in `cache/durable.sqlite-wal` while the server sat idle, so a restart without a clean close (`systemctl restart`, a crash) replayed them all on the server thread at the next start: a 42 MB WAL held a warm boot on the benchmark VPS for 125 to 135 ms. The row deletes that clear the copied outbox now count as writes too, so they get their checkpoint. In a local test, a server killed after a 6,000-write burst and 9 s idle left 726 live WAL frames; it now leaves 1.
- The strict-mode triggers are kept on the server's own SQLite connection (`TEMP` triggers) instead of in the file's schema, and a file from an earlier build loses them at its next boot. SQLite reads the whole schema on each connection's first statement, and every boot opens the checkpoint connections: on the benchmark VPS the triggers were 727 KB of a 773 KB schema (468 triggers), and each such read held a warm boot tick for about 50 ms. In a local test with 40 strict tables, a new connection's first statement takes 4 ms instead of 37 ms.
- Removed exports that no resource called: `lua_query`, `lua_insert`, `lua_scalar`, `lua_single`, `lua_raw`, `lua_update`, `lua_prepare`, `lua_tx`, `lua_drain`, `lua_poll`, `execBlob`, `cis_mode`, `poll`, `flushPlayer`, `checkpoint`, `truncateWal`, `checkpointTruncate`, `triggerSync` and `cis_cdc_tick`. From `lua_poll` on, they already refused every resource except cis_database itself. Use `rawExecute` in place of `execBlob`, and the oxmysql exports in place of `lua_*`.
- A call with fewer values than its SQL has `?` marks (a Lua table whose last values are `nil`) gets `NULL` for the missing ones, as in oxmysql. Before, SQLite took the row but MariaDB refused its copy as a syntax error, seen on the benchmark VPS for an inventory ledger `INSERT` with 14 marks and 10 values.
- New server console command `cis_database_doctor`: checks the folder name, a real `oxmysql` started beside this one, `config.json`, ready, the SQLite file, the WAL checkpoint, the MariaDB copy and the `ALTER` privilege, and names the fix for each problem. It answers the server console only.
- A copy cut short (a crash mid-boot) is marked as such, and a boot with MariaDB down waits for MariaDB instead of serving that half-filled table.
- Strict mode refuses an emoji (any character past U+FFFF) in a `utf8mb3` column, and any character past U+007F in an `ascii` column, with MariaDB's `Incorrect string value`. Before, SQLite took the write and answered ok, MariaDB refused its copy, and the next boot copy removed the row. A column without its own character set takes its table's, then the database's.
- One `REGEXP` statement gets a single work budget for all its rows. Before, the budget was per row, so a long pattern over many long rows held the server thread for the sum (37 s in a test). Past the budget the statement fails with a reason.
- The performance profile's copy in `/dev/shm` has random bytes in its name and is never written over an existing file, so another account on the box cannot plant a file or link to receive it.
- A resource that fires `onResourceStop` for `cis_database` no longer closes the `/cis_db` panel of every admin watching it.
- The change scan checks a table's checksum before it copies the table again. The `AUTO_INCREMENT` raise of beta.2 no longer makes the change scan reload every table after the first boot.
- With `mysql_connection_string` set and the `mysql2` driver missing (a copy of the resource without `node_modules/`), cis_database stays not ready, answers no query, and says on the console how to fix it; `cis_database_doctor` reports it too. Before, it started on whatever SQLite held: on a fresh `cache/` that was nothing, so qbx_core warned that `players` did not exist, qbx_management's `CREATE TABLE` failed on its foreign key to `players`, and that session's writes never reached MariaDB.
- A list bound to any `?` inside `IN ( )` is expanded, as mysql2 formats it: `IN (?, 5)` and the second mark of `IN (?, ?)` too. Before, only a lone `IN (?)` was, so SQLite matched fewer rows than MariaDB for the same statement.
- A Lua table whose first values are `nil` (`{ nil, 'b' }`) binds them as `NULL` in place. Before, the values moved one mark to the left.
- The change scan no longer leaves a SQLite transaction open when MariaDB has an empty table that SQLite does not hold. The game's next transaction failed to begin until the 5 s rescue ended it.
- A transaction takes every form oxmysql takes: a list of `{ sql, params }` pairs, and a list of SQL strings that share the second argument as their values. Before, a pair ran its values as SQL (Renewed-Banking's account setup failed with `near "bcso": syntax error` on a fresh database), and the shared values were dropped, so each `?` bound `NULL`.
- A named value whose key keeps its `@` or `:` (`{ ['@id'] = 1 }`, the mysql-async style) binds, as in oxmysql. Before, it bound `NULL`.
- The `replication.spillMaxBytes` key and the `cis_database_spill_max` convar are gone; nothing read them since the SQLite outbox replaced the spill files. `config.json` keys are read in camelCase only, as documented.

## 1.0.0-beta.2 (internal build, never published)

- A row inserted straight into MariaDB (a web panel, HeidiSQL) while the server is busy is no longer lost, and neither is the game's next row in that table. Before, the change scan waited for 2 s with no query, so on a busy server it never saw the panel row; the game's next insert took the same id, MariaDB refused its copy as a duplicate, and the next boot copy removed the game's row. MariaDB's `AUTO_INCREMENT` counter is now kept far above SQLite's highest id, so a row added in MariaDB gets an id the game never hands out. Needs the `ALTER` privilege; without it the console says so once. Convars `cis_database_id_reserve_ms` and `cis_database_id_gap`.
- A copy MariaDB refuses as a duplicate key is a console warning and a dashboard count. It used to be a debug line, and the write counted as copied.
- The change scan now runs at least every 10 s whatever the load (`cis_database_cdc_force_ms`), skipping a table the game writes during its copy.
- The change scan records each table's starting state only after the first counter raise, so a table edited in MariaDB just after boot is still picked up.

## 1.0.0-beta.1 (internal build, never published)

The first build meant for public release, as a beta.

- The version check knows prereleases: a beta install is told when a newer beta or the final `1.0.0` is out.
- README "Going back to oxmysql": how to switch back with nothing left behind.
- Every boot copies each table from MariaDB again, so edits made in MariaDB while the server was stopped (a panel, HeidiSQL, a stretch on oxmysql) are what the game reads. Earlier `node:sqlite` builds kept their own copy: they answered the old rows, and a new row could take an id MariaDB had already given, so its copy to MariaDB failed. A table with writes still waiting for MariaDB keeps its copy until they are in, then is copied once. A boot with MariaDB down does the same for every table once MariaDB is back.
- Game SQL runs on SQLite inside the FXServer Node 22 isolate (`node:sqlite`, with a `sql.js` fallback), so a query does not wait on a network round trip.
- Provides `oxmysql`, `mysql-async` and `ghmattimysql`. Existing resources run unchanged; `@oxmysql/lib/MySQL.lua` is served by this resource.
- MariaDB stays the system of record. On boot the game copy is filled from MariaDB; writes are copied back in the background, in order, from an outbox kept in the SQLite file, so a MariaDB outage loses nothing.
- A `cache/` restored from a backup or copied from another install on the same MariaDB is found older than MariaDB at boot: writes made since are still copied to MariaDB, and the tables are refilled from MariaDB. Those writes are never counted as already copied.
- Edits made to MariaDB outside the game (a web panel, a manual query) are picked up while the server runs.
- `/cis_db` admin dashboard, gated by the ACE `cis_database.dashboard`.
- Version check against the latest GitHub release at start.
- Benchmark against oxmysql on MariaDB, on the same box, rerunnable with one command: see `bench/`.
- Return types now match oxmysql: `DATETIME` and `TIMESTAMP` columns come back as epoch milliseconds, `DATE` as milliseconds at local midnight, and `TINYINT(1)` / `BOOLEAN` as `true` / `false` (`prepare` and `rawExecute` turn the dates only, as oxmysql does). Earlier builds returned the date text and `1` / `0`. A script written against oxmysql needs no change; one written against those builds may.
- Write results match MariaDB: `ON DUPLICATE KEY UPDATE` counts 1 for a row found with nothing to change, and an insert of several rows reports the first new id.
- `ON DUPLICATE KEY UPDATE` that changed a row reports that row's `AUTO_INCREMENT` id as `insertId`, as MariaDB does; one that changed nothing reports 0. Earlier builds reported 0 for every update.
- A table without an `AUTO_INCREMENT` key reports `insertId` 0, as MariaDB does, instead of SQLite's hidden row number.
- `ALTER TABLE ... MODIFY` or `CHANGE` that adds `AUTO_INCREMENT` to a column, and `AUTO_INCREMENT = N` on a table, now take effect.
- `SELECT *` and `SHOW COLUMNS` keep the column order the DDL gave (`AFTER`, `FIRST`), and `DECIMAL` columns read as mysql2's exact decimal strings (`"5.30"`).
- `UUID()` (a version 1 UUID) and `UUID_SHORT()`, also as column defaults: an `ADD COLUMN ... DEFAULT UUID_SHORT()` fills each row with its own value.
- A whole number past 2^53 (a Discord id in a `BIGINT`, `UUID_SHORT()`) reads as its exact decimal string, as mysql2 gives it. Earlier builds failed the read.
- A read SQLite would answer differently from MariaDB (a `SUM` or `ROUND` result, a text column compared with a number, accented text, an `ENUM` or `FLOAT` column, and the other cases in README "Reads MariaDB answers") is answered by MariaDB when one is configured, after the outbox for its tables is copied. While MariaDB is down or past `cis_database_maria_read_ms`, that read fails with the reason instead of answering SQLite's value. Rules key on the statement's shape, column types and bound values, never on names.
- With no MariaDB configured, a read SQLite cannot run says so in its error.
- `sql.js` fallback: dates, `TINYINT(1)` and `DECIMAL` columns are now cast as on `node:sqlite`, and a boot with MariaDB down waits for MariaDB instead of starting from the old snapshot, which lacked recent writes and could give a new row an id MariaDB already had.
- `GREATEST`, `LEAST`, `FIND_IN_SET` and `JSON_LENGTH` whose arguments hold a backticked name or a string translate correctly; ``GREATEST(0, `jackpot` + ?)`` used to fail.
- `UPDATE ... SET` and `ON DUPLICATE KEY UPDATE` run their assignments left to right, as MariaDB does: in `SET streak = streak + 1, best = GREATEST(best, streak)`, `best` sees the new `streak`. Earlier builds gave every assignment the old row, so SQLite and MariaDB stored different values for the same statement.
- `LAST_INSERT_ID(expr)` makes `expr` the insert id and the next `LAST_INSERT_ID()`, as MariaDB does. `ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id)` (esx_license) now reports the id of the row it found instead of 0, and counts 1 affected row for it, as MariaDB does.
- `SELECT LAST_INSERT_ID()`, `ROW_COUNT()` and `FOUND_ROWS()` are always answered by the engine. A build that sent such a read to MariaDB got 0 from a connection that had run no insert.

Install: stop `oxmysql` (never run both), put the folder in `resources` as `cis_database`, set `mysql_connection_string`, and start it before every resource that runs SQL. No manual SQL is needed. Full steps: `README.md`.
